# Review of the Codex accepted-reply reconciliation change

Read-only review of the integrated `CodexAcceptedReplies`, live-window cursor/head state, ViewModel ownership, Activity presentation/dismissal, and added tests. I reviewed only the requested Codex-related hunks in the shared modified files; unrelated work in those files is not assessed here. No tests were run and no source was changed.

## Findings

### Confirmed race: matching journal row can be consumed before acceptance is registered

`PaneViewModel.sendReply` captures a correct pre-send baseline before launching the guarded send (`android/app/src/main/java/com/lateapex/collie/ui/PaneViewModel.kt:236-241`). However, it adds the accepted item only after `CodexReplyGuard.send` returns success (`:281-290`). Meanwhile the normal pane polling loop continues; every successful pane poll calls `loadTranscript()` (`:696-715`), which merges the live chat page and calls `acceptedReplies()?.reconcile(page)` (`:775-786`).

If the journal records the new user `response_item` after Codex takes Enter but before the reply guard finishes its confirmation read, that page advances `LiveChatWindow` and contains the matching upsert while there is no `Pending` accepted item yet. The later success inserts the pending item with the earlier pre-send baseline; the immediate `load()` at `PaneViewModel.kt:309` then polls using the already advanced `chatWindow.after`. The next response is empty/304, so the matching user row is never offered to the reconciler again and the preview persists until manual dismissal. This is especially plausible because the guard explicitly reads the pane after Enter while background polling is independent, and Codex may journal the user row during that interval.

**Concrete fix:** after `accepted.accept(clean, baseline)`, reconcile against the currently held live-window snapshot as well as future `upserts`, preserving the original acceptance baseline checks (`gen`, `rev > baseline.rev`, `seq > baseline.head`, exact complete user text). A small `LiveChatWindow` snapshot method or a reconciler method taking held `(gen, rev, entries)` avoids synthesizing an invalid wire response. Add a deterministic ViewModel test where a matching same-generation user turn is returned by a background chat poll while the fake submit guard is paused, then allow send success with no subsequent chat changes. The final state must be reconciled without another write. The existing pure test only exercises a turn arriving after `accept()`; the current ViewModel test never returns any live chat page.

### No end-to-end positive reconciliation test currently exercises the ViewModel wiring

`CodexAcceptedRepliesTest` tests the pure helper’s exact-turn rules, but `PaneViewModelTest.acceptedCodexInputSurvivesUnrelatedOutputAndIsIsolatedByOriginWithoutReplay` (`PaneViewModelTest.kt:592-622`) only tests retention, switching origins, dismissal, and write count; its fake API does not override `chat`, so chat returns the default unavailable result. There is no test proving a production `PaneViewModel` chat poll invokes the reconciler and clears a real accepted item. The race above is why the helper-only positive test is not sufficient.

The Activity test `codexAcceptedPreviewUsesRetainedStateInsteadOfMirrorChangesOrATimer` (`PaneActivityTest.kt:52-69`) manually passes a `PaneUiState` to two distinct activities. It verifies rendering behavior, not retained ViewModel ownership or a real configuration-change/rotation. The architecture appears to support configuration changes because the accepted map is a `PaneViewModel` field, but the test does not prove it. Add a `ViewModelStore`/Robolectric recreation test or test the real factory/provider lifecycle rather than describe this as a recreation proof.

### Process death remains an explicit gap

The accepted state is an in-memory map in `PaneViewModel` (`PaneViewModel.kt:119-122`), so it survives Activity recreation while that ViewModel instance survives, but not process death. This matches the requested ViewModel-owned fix and avoids persisting potentially sensitive message text. Record this as a deliberate boundary; do not claim process-restoration coverage. The new test comment currently says “recreated view” but does not exercise process or ViewModel restoration.

### Legacy history fallback cannot reconcile a Codex item

The accepted-reply reconciler is only invoked in the successful `/chat` branch (`PaneViewModel.kt:775-786`). When `/chat` is missing and the ViewModel falls back to `/history` (`:791-810`), it merges history entries but never reconciles accepted Codex items. The new baseline is also unavailable unless a live `chatWindow.after/head` was populated. This is conservative and does not cause a false confirmation, but means accepted previews on a bridge without `/chat` can never auto-reconcile. Either retain the documented “dismiss to clear” limitation for legacy/unsupported live chat, or add a safe history reconciliation path with an established baseline and tests. The HTTP contract explicitly says a member one release behind may answer 404 to `/chat` and this is version skew, not an empty session (`/home/chris/git/collie/bridge/types.ts:828-832`).

## Conclusion and validation boundary

The integration correctly separates terminal acceptance from journal visibility, retains items per server origin in the ViewModel, requires a newer live user turn before removing one, exposes dismissal, and does not retry. I found one concrete false-negative race: an upsert arriving after the pre-send baseline but before the acceptance is inserted advances the live cursor and is not replayed to the new pending item. Please fix that and add the paused-send/background-poll fixture before treating reconciliation as verified. Legacy `/history` remains conservative but cannot clear accepted state; process-death restoration is not implemented. This is source review only; no test results, emulator evidence, or live Codex verification are claimed.
