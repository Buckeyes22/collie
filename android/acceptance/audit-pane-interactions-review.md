## Findings

### P1 — Microphone permission result does not revalidate the recording guard

`PaneActivity.kt:213–215` starts recording unconditionally when the permission result is granted. The initial tap path in `toggleSpeechRecording()` checks availability, busy state, direct typing, write gate, semantic keyboard ownership, and no-echo state at lines 594–610; `startSpeechRecording()` rechecks only availability/busy/already-recording/write gate at lines 613–616. If pane state changes while Android's permission surface is active (for example the pane becomes sending or a semantic/no-echo prompt appears), the granted callback can start the microphone in the newly unsafe state. The current control renderer also allows an already-recording Stop affordance while recording, but that does not address starting after stale permission state.

Suggested correction: route the callback through one shared “can start now” predicate that rechecks `currentState.pane != null`, `!currentState.sending`, `!directTyping`, no semantic keyboard owner/no-echo prompt, `!composerMediaBusy`, and `PaneWriteGate`; if the predicate fails, leave recording stopped and show the applicable explanation. Keep Stop enabled while recording. Add a deterministic `PaneActivityTest` that requests permission in a safe state, renders a semantic prompt or sending state before granting, invokes the registered result callback, and asserts `ComposerSpeechRecorder.start()` was not reached / recording status is absent. Also cover pane disappearance/read-only transition.

### P2 — Repeated arrow-key hold work is not explicitly lifecycle-cancelled

`bindKeyRepeat()` stores `engaged`, `repeats`, `tick`, and `engage` in a touch-listener closure (`PaneActivity.kt:1291–1339`). It removes callbacks on `ACTION_UP` and `ACTION_CANCEL` (`1319–1322`) and only commits on an engaged `ACTION_UP` (`1323–1333`), which correctly avoids sending a cancelled gesture. However, `onStop()` (`379–392`) does not cancel any active hold callbacks or reset their state; `onDestroy()` removes all handler callbacks (`395–400`) but a stopped Activity may remain alive. Android lifecycle guidance treats `onStop` as the point where the UI is no longer visible. The implementation relies on the View receiving `ACTION_CANCEL` during every loss-of-visibility transition, which is not established by the source tests.

Suggested correction/test: retain the active repeat cancellation closure in Activity state and cancel/reset it in `onStop()`; then test down+hold, transition Activity to stopped before the scheduled engage/tick, advance the main looper, and assert no key sequence is sent and no callbacks remain. Existing `PaneActivityTest.repeatedKeysCommitOnlyOnAnEngagedActionUp` covers commit/cancel touch events but not Activity lifecycle interruption. This is a lifecycle test gap; I did not classify it as a proven remote write because `ACTION_CANCEL` may arrive first on target devices.
