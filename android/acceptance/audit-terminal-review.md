### Codex submission evidence and gap

The earlier Codex report’s sentence implying a Codex prompt-binding device test was inaccurate. `PaneComposerDeviceTest.kt` exists, but contains no Codex/reply/send case (verified with a source search). The Codex path has unit/fixture and Robolectric coverage, not a Codex-on-device send test.

The production guard’s “consumed” test is narrower than that word suggests. `/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/ui/terminal/CodexReplyGuard.kt:39-48` returns success once `PromptBinding.composerRegion("codex", fresh)` becomes non-null after Enter; that proves the message left the visible composer, not that a model turn has begun. Android clears its draft on the resulting `ok` in `/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/ui/PaneViewModel.kt:272-279`.

The pinned Codex source confirms multiple possible destinations for that cleared composer. At `/tmp/collie-codex-upstream-20261010/codex-rs/tui/src/bottom_pane/chat_composer.rs:3131-3195`, Enter first flushes a paste burst; the queue path prepares/expands pending pastes and returns `InputResult::Queued`, which clears the visible textarea. The normal submission path is at lines 3210–3247. `/tmp/collie-codex-upstream-20261010/codex-rs/tui/src/chatwidget/input_flow.rs:49-94` shows `Submitted` can be sent immediately or retained in Codex’s input queue depending on session/turn/recovery state; explicit `Queued` also transfers into that queue. The TUI can therefore own a queued message while its visible composer is empty. The large-paste threshold is 1,000 characters (`chat_composer.rs:443`); Enter calls `handle_paste_burst_flush` before dispatch (`3131-3143`), and `chat_composer.rs:1887+`/tests at `6239-6247` document the `[Pasted Content N chars]` element mapping. Android’s `codePointCount` and exact `>1,000` token acceptance match this pinned behavior.

A narrow reconciliation/visibility gap remains unresolved: `/home/chris/git/collie/bridge/journal/codex.ts:515-516` declares Codex has no queue in its session-log format, while Codex’s TUI can hold a local pending queue before writing the eventual user turn. Thus a successful empty-composer read can clear the Android draft before the transcript endpoint has a Codex user-turn or queued-preview to show. That does not prove message loss—the TUI owns the pending item—but the current Android test’s final empty composer cannot distinguish a dispatched user turn from a TUI-retained queued item. Existing bridge evidence `/home/chris/git/collie/bridge/journal/codex.test.ts:504-533` covers a working-turn steer once represented as a rollout user row and deduplicated against its event twin; it does not cover pre-dispatch local queue ownership. I recommend an isolated regression fixture proving the relevant empty-composer-plus-pending-queue path and a product decision for state text: “accepted by Codex / queued” versus “sent.” Do not retry or retype on that state; reconcile by a later matching transcript entry if the journal supplies one. No source correction is claimed in this read-only audit.

### Semantic detector coverage and exclusions

- Claude Code official docs are not treated as stable terminal markup requirements. Collie’s pinned notes above define the measured cases. Claude free-text rows (plan feedback, notes, “Other” answer) are excluded from digit actions; identified input ownership locks interaction until it can be safely handed back.
- Codex trust, permission, and ask cards are only lifted on validated signatures. The test captures include Codex 0.154–0.158 per `/home/chris/git/collie/android/app/src/test/resources/codex/README.md:12-24`; their provenance is public disposable-session fixtures. The Android parser does not implement the Codex app-server protocol.
- Grok ask, picker, permission, and plan surfaces are lifted only when their measured grammar confirms the expected footer and option set. Unrecognized/checkbox shapes stay raw.
- AGY known dialog recipes are supported; write-in rows are not buttons. Unknown dialog content remains terminal text.
- OpenCode 1.18.32/1.18.33 question and permission prompt recipes in Collie’s notes are **not** implemented in Android’s `AgentSemanticParser`; the raw terminal remains visible and `PromptBinding` only supplies the composer write preflight. This is an intentional exclusion, not a passed semantic-dialog audit.
- OMP has no native semantic detector; it remains raw. Its collection is context-only here.
- `TerminalLinks`, colors, wrapping, ANSI and tables cover the Android view representation and local regression behavior; they are not guarantees of every terminal emulator’s cell width or every agent release.

No source defect beyond the queued-versus-sent observability gap described above is confirmed by this review. No claim is made about other device widths, unsupported agent versions, or live sessions.
