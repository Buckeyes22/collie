# Follow-up audit: transport privacy, media-send guard, and evidence coverage

Date: 2026-10-10  
Review scope: current dirty Android implementation changes affecting Codex accepted-message privacy/scope and media-send busy handling; supporting repository connection lifecycle and relevant documentation/dependency evidence. Read-only source review; no production edits or tests run.

## Findings

### F1 — Hands Free transcription AutoSend is suppressed by the pending-media guard

**Confirmed behavior defect.** In `/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/ui/PaneActivity.kt:633-646`, `stopSpeechRecording()` sets `composerMediaBusy=true`, awaits transcription, calls `applyComposerMediaResult(...)`, and only then clears busy. For a `ComposerMediaResult.AutoSend`, lines 691-696 place the transcript in the input and call `sendReplyWithConfirmation(...)`. That method returns immediately at lines 2064-2067 whenever `composerMediaBusy` is true. Thus every successful Hands Free transcription result reaches the normal send wrapper while its own operation still holds the busy flag; the transcript remains in the draft and the intended automatic send does not happen.

The guard does prevent a manual send while an upload/transcription can still modify and later clear the draft. Existing coverage in `/home/chris/git/collie/android/app/src/test/java/com/lateapex/collie/ui/PaneActivityTest.kt:72-101` verifies pending media blocks Ctrl+Enter and preserves draft text. `/home/chris/git/collie/android/app/src/test/java/com/lateapex/collie/ui/ComposerMediaTest.kt:81-123` verifies the pure media policy can produce `AutoSend`, but no test covers the Activity ordering or successful Hands Free submission. Recommended correction: keep manual submission blocked while work is pending, but release the busy state before dispatching the completed AutoSend, or route that completed result through a narrowly scoped internal submission entry point. Add an Activity-level regression proving a completed Hands Free transcript submits exactly once, and retain the existing test that a user submission during pending media is blocked without clearing the draft.

### F2 — Codex accepted message text is retained by origin, not by connection identity

**Confirmed same-origin connection-scope leak in UI state.** `/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/ui/PaneViewModel.kt:119-122` stores `CodexAcceptedReplies` in a map keyed only by `connection.origin.value`. The connection collector at lines 141-159 clears pane/transcript and other connection-bound state on any `Connection` change, but repopulates `codexAcceptedReplies` from that origin-keyed map. `CodexAcceptedReplies.texts` contains accepted prompt text awaiting transcript reconciliation (see `/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/ui/CodexAcceptedReplies.kt`). Switching between two pairings for the same origin therefore restores the prior pairing's pending prompt text into the new pairing's UI state. The existing regression at `/home/chris/git/collie/android/app/src/test/java/com/lateapex/collie/ui/PaneViewModelTest.kt:592-622` proves isolation only for a *different origin* and explicitly restores the original text when switching back; it does not cover same-origin connection replacement.

Recommended correction: clear pending accepted-message snippets on every connection identity change, including a new pairing for the same origin. Do not use bearer tokens as map keys or retain them in logs. If product behavior requires restoring per-pairing pending text, introduce a non-secret opaque identity with lifecycle/retention limits and test its privacy semantics. Add a same-origin/different-label-and-token switch test asserting the former accepted text is absent. Keep existing transcript reconciliation behavior within one unchanged connection.

### Connection lifecycle assessment

The current transport/repository hardening is directionally sound for stale results. `/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/data/CollieRepository.kt` binds requests and cache keys to `Connection` identity, rechecks write authorization after snapshot verification, and rejects results if the selected connection changes. `PaneViewModel.kt:141-145` cancels its active mutation on observed connection change and clears pane/transcript state. This prevents a completed response from being projected into the replacement connection's UI; it cannot retract a request already delivered to the old server before cancellation. Existing `/home/chris/git/collie/android/app/src/test/java/com/lateapex/collie/ui/PaneViewModelTest.kt:695-710` exercises switching during Codex submission and checks the draft is retained and the new pane remains empty. This does not address F2's accepted-message map, which is independent of the canceled mutation.

### Diagnostics route matching

`/home/chris/git/collie/android/app/src/main/java/com/lateapex/collie/diagnostics/DiagnosticsInterceptor.kt` identifies pairing requests by decoded trailing route segments `api/pair`, rather than only the unmounted exact path. This covers a bridge mounted below an origin path and errs toward additional redaction for a trailing matching path. Review of this change found no privacy regression; test evidence is in `/home/chris/git/collie/android/app/src/test/java/com/lateapex/collie/diagnostics/DiagnosticsInterceptorTest.kt` (including mounted-path pairing coverage).
